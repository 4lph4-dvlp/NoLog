  </what-built>
  <how-to-verify>
    **Pick the posts.** Use **every** public post if there are five or fewer; otherwise at least **three**, and include among them at least one of the posts Phase 7 observed failing (`07-EVIDENCE.md`). One post is not a sample — SC#1 says "across multiple posts", and a single post can pass by luck if any residual cause is intermittent.

    **For each post, run this four-step cycle.** Use `GET`, not `-I`/HEAD: HEAD handling can differ from GET for some cache paths and has not been confirmed either way for this route, so GET is the conservative choice (`08-RESEARCH.md` Assumption A2).

    ```
    SITE=<CONFIG.site.url>
    ID=<post id>
    check() { curl -sD /var/tmp/h.$$ -o /var/tmp/b.$$ "$SITE/post/$ID"; \
      printf 'cache=%s ' "$(grep -i '^x-vercel-cache' /var/tmp/h.$$ | tr -d '\r' | awk '{print $2}')"; \
      printf 'failSentence=%s ' "$(grep -c 'could not be loaded right now' /var/tmp/b.$$)"; \
      printf 'emptySentence=%s\n' "$(grep -c 'has no content yet' /var/tmp/b.$$)"; }
    ```

    1. **Request A**, right after the deploy — run `check`. Expect `cache=MISS`. Every deploy invalidates the whole cache, so this is a cold fill and one genuine regeneration under the fixed code. **It proves nothing on its own** — this is exactly the "one lucky load shortly after a deploy" Pitfall 15 names. Record it anyway.
    2. **Wait more than 180 seconds without visiting that post URL.** Not 180 exactly — comfortably past it. Do not warm it with a browser tab in the background; an accidental request restarts the window.
    3. **Request B** — run `check`. Expect `cache=STALE`. This response still serves Request A's cached output while a background regeneration fires; its body is *old* and is not evidence.
    4. **Request C**, a few seconds after B — run `check`. Expect `cache=HIT`, now serving the regeneration Request B triggered. **This is where the assertion belongs.** On this request, both `failSentence` and `emptySentence` must be `0`.

    **Why the two zeroes are the body check.** The template guarantees that when there is nothing to render, exactly one of the two sentences appears — there is no path that renders neither. So both counts being `0` means the Notion renderer ran, i.e. the body is there. Corroborate at least one post visually in a browser as well.

    **If the values do not match.** Report what you actually saw. Common legitimate variants: a `MISS` where `STALE` was expected (the entry was evicted rather than expired — treat it as a fresh cold generation and assert the body on that response); a second `STALE` (the background regen had not finished — wait and request again). Anything else, including any `failSentence=1`, is a finding, not a retry-until-green situation.

    **Record everything.** Create `.planning/phases/08-content-rendering-fix/08-CACHE-EVIDENCE.md` with one row per request per post: post id, request letter, UTC time, observed `x-vercel-cache` value, `failSentence`, `emptySentence`. Observed values only — no inferred cells, no "as expected".

    **CONT-05 on the deployed site.** Also confirm, on any real post, that neither sentence appears (both counts `0`). The two *fallback* states themselves were observed under the local production build in plans 08-02 and 08-03 — legitimately, because CONT-05's branch is a control-flow property that behaves identically wherever the code runs, exactly the reasoning `07-UAT.md` used for Phase 7's SC#3/SC#4. Pitfall 12 constrains *environmental* behaviour, which the branch is not. Note this reasoning in the evidence file rather than leaving the deployed empty-state check silently unrun; do **not** republish the throwaway empty page from plan 08-02 to production to force it.
  </how-to-verify>
