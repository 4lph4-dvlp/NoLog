## Phase Goal

**As a** blog visitor, **I want to** hand over my email address on the site and be told plainly whether
it went through, **so that** I get notified when a new post goes up — while a forker who never
configured Resend ships a site where that form, and the secret behind it, simply do not exist.

_Story provenance: reused verbatim from `03-02-PLAN.md` § Phase Goal, which is where this phase's
approved user story lives. The ROADMAP `**Goal:**` line for Phase 3 is not in user-story format; no
new story was invented here (see § Flagged assumptions)._

<objective>
Close the one genuine gap left by this phase: `03-VERIFICATION.md`'s failed truth for ROADMAP SC#4's
rate-limit half, blocking SUB-04. The per-IP rate limiter added in plan 03-02 keys entirely on the
FIRST comma-separated entry of `x-forwarded-for`, a header the client supplies. An attacker on one
machine varying that one header per request gets a fresh counter bucket every time, so the
"five per ten minutes" guarantee never engages. This was reproduced twice — by `03-REVIEW.md` (CR-01,
Critical) and independently by verification: 8 POSTs with distinct fabricated header values, 0 of 8
refused.

The same defect has a second half. The sweep in `isRateLimited` evicts only entries whose window has
EXPIRED, so a high-cardinality spoofing burst keeps every entry fresh and un-sweepable for a full ten
minutes, growing the map by roughly one entry per request — which contradicts the module's own comment
claiming the window is what bounds it.

This plan replaces the identity derivation with a platform-first, fail-closed tiering, and adds a hard
ceiling on distinct keys that holds independent of expiry. It is strictly additive over executed work:
plans 03-01, 03-02 and 03-03 are complete and are not touched.

Purpose: without this, the phase goal's "resistant to bot/enumeration abuse" clause is false for the
rate-limiting mechanism, and no later roadmap phase (4 Notify Route, 5 Production Cutover,
6 Documentation) addresses IP-derivation hardening — so it is not deferrable.

Output: `apps/web/src/app/api/subscribe/route.ts` with a rate limiter whose key an attacker cannot
mint and whose memory an attacker cannot unbound, proven by an executable
reproduction-then-fix probe that needs no Resend credentials.
</objective>

## Header verification record (the load-bearing research step)

The review demanded the exact platform header name be checked against current Vercel docs rather than
assumed. It was fetched directly during planning of this plan.

| Field | Value |
|---|---|
| **Source** | `https://vercel.com/docs/headers/request-headers` |
| **Fetched** | 2026-07-26 (this planning session) |
| **Doc `last_updated`** | 2025-12-13 |
| **Runtime in scope** | `nodejs` — the runtime `route.ts` declares |

What the docs actually say, quoted:

- `x-forwarded-for` — "The public IP address of the client that made the request." And, decisively:
  "If you are trying to use Vercel behind a proxy, we currently overwrite the `X-Forwarded-For` header
  and **do not forward external IPs**. This restriction is in place to prevent IP spoofing." A
  documented Enterprise-only add-on ("Trusted Proxy") is the explicit opt-in required to allow a custom
  `X-Forwarded-For` value.
- `x-vercel-forwarded-for` — "This header is identical to the `x-forwarded-for` header. However,
  `x-forwarded-for` could be overwritten if you're using a proxy on top of Vercel."
- `x-real-ip` — "This header is identical to the `x-forwarded-for` header."
- All three are listed under "The following headers are sent to each Vercel deployment", i.e. the
  platform injects them on every request.

**Conclusion — option 1 lands.** `x-vercel-forwarded-for` is the platform-owned variant, documented as
resilient to exactly the overwrite case that makes `x-forwarded-for` untrustworthy, so it is the
preferred key source. `x-real-ip` is the documented equivalent and serves as the second tier.

**What the docs do NOT say, stated plainly rather than glossed.** No page uses the words "cannot be
overridden by the client" about any of these headers. The strongest documented anti-spoofing statement
is the `x-forwarded-for` overwrite quoted above. This plan therefore does not rely on a
non-overridability claim the docs do not make: it prefers the platform-owned header, applies the
review's option-2 last-entry rule with the trusted-hop assumption stated in code, treats a bare
`x-forwarded-for` as untrustworthy, AND lands the option-3 hard ceiling regardless. The correctness of
the fix does not depend on the header being unforgeable.

**Trusted-proxy-count assumption, recorded as required.** Exactly ONE trusted hop — the Vercel edge —
produces the platform headers on a supported deployment. If such a header ever carries multiple
comma-separated entries, the LAST is the one that hop appended and is the one used. This assumption is
stated in a code comment at the derivation, not only here.

**Correction to `03-RESEARCH.md`.** That document's Architecture Patterns Pattern 2 recommends "take
the first entry" of `x-forwarded-for` and its Assumptions Log A2 treats the header as reliable on a
direct Vercel request. The first-entry recommendation is the proximate cause of CR-01 and is superseded
by this plan. `03-RESEARCH.md` is a historical artifact and is deliberately NOT edited; this section is
the correction of record.

`getRateLimitKey` tries three header sources in strict order, first non-empty match winning:

1. `x-vercel-forwarded-for` — the platform-owned client IP. Trusted.
2. `x-real-ip` — the documented platform-injected equivalent. Trusted.
3. `x-forwarded-for` — present but with neither platform header alongside it. NOT trusted.

nearest the client. Encode the reason in a comment at that line: exactly one trusted hop, the Vercel
edge, produces the platform headers on a supported deployment, so if such a header ever carries several
entries the last is the one that hop appended. Treat an entry that trims to the empty string as no
match and fall through to the next tier.

For tier 3 the derived value is deliberately DISCARDED as a key. Return the module constant
`ATTEMPTS_UNTRUSTED_KEY`, set to the literal `"untrusted"`, so every request whose only identity claim
is a client-suppliable header shares ONE bucket. This is the substance of the CR-01 fix: an attacker
varying that header per request no longer mints a bucket per request, they accumulate in a single
bucket and are refused on their sixth attempt. Record in a comment why the value is discarded rather
than used, so a later reader does not "restore" it as an optimization.

When none of the three headers yields a non-empty entry, return the existing literal `"unknown"`,
unchanged from D-12: a single shared bucket at the same five-per-ten-minutes limit, so stripping every
header is not a bypass and local development against one shared key still works. Keep `"unknown"` and
`ATTEMPTS_UNTRUSTED_KEY` as two DISTINCT literals — never merge them. Merging would let a spoofing
burst against tier 3 throttle the header-less traffic that local development and any unusual proxy
configuration land on, and that collateral damage is avoidable for the cost of one extra constant.

State the deployment tradeoff in a comment at the tier-3 branch, because it is a real cost and must not
read as an accident: on Vercel a platform header is always present, so tier 3 is unreachable in
production and per-visitor counting is unaffected. On a host that supplies no platform header, every
visitor collapses into one shared bucket and the limit becomes site-wide rather than per-visitor. That
is over-throttling, never under-throttling, which is the same fail-closed direction D-12 already chose,
and Vercel is this template's only supported host per PROJECT.md's constraints.
