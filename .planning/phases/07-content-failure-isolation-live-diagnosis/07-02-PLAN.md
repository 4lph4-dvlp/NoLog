<objective>
Close ROADMAP SC#4: a post that exists and is public must never respond 404 because of a content-fetch failure.

Purpose: `07-RESEARCH.md` established — and this plan acts on — the fact that `NologClient.getPost()` (`packages/core/src/client.ts:311-338`) wraps its whole body in `try { … } catch { return null }` and therefore **never throws**. A transient 429/500/network failure returns `null` indistinguishably from a genuine 404, so `post/[id]/page.tsx:59-61` already 404s live posts today. `packages/core` is a published npm package and must not be modified (REQUIREMENTS.md D-05), so this cannot be fixed by wrapping the call in a `try` — there is nothing to catch.

Output: an app-level discriminator that asks Notion directly whether the page exists, but only on the path where `getPost()` has already returned `null`; and the `PostUnavailable` state `07-UI-SPEC.md` specifies.
</objective>

## THE OPEN ENGINEERING QUESTION — RESOLVED

`07-RESEARCH.md` Open Question 1 / `07-CONTEXT.md` D-12's correction note / `07-UI-SPEC.md`'s Scope section all defer one decision to this plan. It is resolved here as **option (a): add an app-level discriminator**, not option (b) (accept a residual gap).

**Rationale.**
1. ROADMAP SC#4 states the requirement unconditionally, and D-12's *intent* was locked in discussion — only the *mechanism* was open. Accepting (b) would leave a locked success criterion knowingly unmet.
2. `07-UI-SPEC.md` was authored, checked, and approved (6/6) on the premise that this component is reachable. Choosing (b) would ship a written-but-unreachable `PostUnavailable.tsx`, which the UI-SPEC itself flags as the outcome to avoid.
3. The mechanism is cheap and constraint-free: one extra Notion REST call, on a path that has already failed, with no new dependency and no change to `packages/core`.

**Why the obvious alternatives do not work — record these, they are the load-bearing findings.**
- *"Just retry `getPost(id)`."* `apps/web/src/lib/notion.ts:23-25` wraps `getPost` in React `cache()`. A second call inside the same render returns the **memoised** `null`, not a fresh attempt. A retry through that wrapper is a no-op by construction.
- *"Parse the page's `status` property in the app."* That re-implements `packages/core`'s property extraction in a second place. STATE.md's 2026-07-25 CORRECTION records exactly this defect class (CR-01: the property is lowercase `status`, mis-derived once already at real cost). Do not re-derive it.
- *"Wrap `getPost()` in a `try`."* `07-RESEARCH.md` Pitfall A: the function cannot throw, so the catch is dead code and the diff changes nothing.

**Happy-path cost:** zero. The discriminator is called only inside the existing `if (!post)` branch. A post that renders successfully makes exactly the same Notion calls it makes today.

**Accepted behaviour changes, recorded rather than discovered later:**
- A deployment with `NOTION_TOKEN` unset returns `"missing"` immediately with no outbound call, so an unconfigured fork behaves byte-identically to today (a 404), plus one latched operator log line.
- A page that Notion returns successfully (HTTP 2xx) but that `getPost()` still declines is classified `"missing"`. This preserves today's behaviour for the non-public and unparseable-page cases and deliberately does not attempt to re-derive why.
- `generateMetadata`'s not-found branch keeps its existing `Post Not Found` title (out of `07-UI-SPEC.md`'s copywriting scope, and D-14's "do not design the wording before the cause is known" applies). Only `robots` is added. The title/state mismatch on the transient page is a known cosmetic gap — record it in 07-VERIFICATION.md, do not fix it here.

**`apps/web/src/lib/post-availability.ts` (new).** Export `type MissingPostVerdict = "missing" | "unavailable"` and `async function classifyMissingPost(pageId: string): Promise<{ verdict: MissingPostVerdict; detail: string }>`.

Its contract, stated in a head comment: it is called **only** after `getPost()` has already returned `null`, it makes at most one outbound request, and it **never throws**. The head comment must also record the two mechanisms it deliberately avoids and why — the React `cache()` memoisation that makes a `getPost` retry a no-op (`apps/web/src/lib/notion.ts:23-25`), and the CR-01 property-extraction duplication risk (STATE.md 2026-07-25 correction) — so a future edit does not "simplify" it back into one of them.

Resolution order, first match wins:
1. `process.env.NOTION_TOKEN` unset or empty → verdict `missing`, reason `unconfigured`, **no network call**. Emit one latched `[PostPage:post]` `console.error` per serverless instance (module-scope boolean latch copied from `subscribe/route.ts`'s pattern, with the "Further occurrences in this instance are not logged." sentence). An unconfigured deployment has no posts at all, so a 404 is the truthful answer and today's behaviour is preserved exactly.
2. `parsePageId(pageId)` from `notion-utils` returns falsy → verdict `missing`, reason `invalid-id`, no network call. A string that is not a Notion page identifier cannot name a real page, and refusing it here is what keeps caller-controlled input out of the outbound URL.
3. Otherwise issue one `fetch` to the official pages endpoint. Build the URL as the constant prefix `https://api.notion.com/v1/pages/` concatenated with the value **returned by `parsePageId`**, never with the raw parameter. Method GET; headers `Authorization: Bearer <NOTION_TOKEN>` and `Notion-Version: 2022-06-28` (copy the version literal from `packages/core/src/client.ts`'s `NOTION_VERSION`). Pass `cache: "no-store"` — this call must never be served from Next's Data Cache, or it would echo the very failure it is trying to discriminate.
   - `res.status === 404` → verdict `missing`, reason `notion-404`. Notion authoritatively answered.
   - `res.ok` → verdict `missing`, reason `notion-ok`. The page is fetchable, so `getPost()`'s `null` came from a non-public status or an unparseable page object; both are legitimately not-found for a reader.
   - any other status → verdict `unavailable`, reason `notion-error`.
4. The `fetch` throws (DNS, TLS, timeout, abort) → verdict `unavailable`, reason `request-failed`. Catch it inside this function; never let it escape.

`detail` is a single-line JSON string in D-05's payload shape, ready for the caller to append after its bracket prefix. Ungated it carries `verdict` and `reason` only. When `isDiagnosticsEnabled()` (imported from `@/lib/notion-x`) is true it additionally carries `status`, `contentType` from `res.headers.get("content-type")`, `bodyExcerpt` as the first 200 characters of `await res.text()`, `pageIdShape`, and `pageIdLength` — the same field names and 200-character cap plan 07-01 established (D-03). Never place the `Authorization` header value, `NOTION_TOKEN`, or the raw page id into the payload.
