## Phase Goal

**As a** blog visitor, **I want to** hand over my email address on the site and be told plainly whether it went through, **so that** I get notified when a new post goes up — while a forker who never configured Resend ships a site where that form, and the secret behind it, simply do not exist.

<objective>
Expand the proven tracer slice with the abuse-resistance layer that SUB-04 requires and that
`FEATURES.md` establishes as the mandatory compensating control for skipping double opt-in: a per-IP
rate limit and a server-side honeypot check, inserted into the route handler at exactly the positions
D-23 specifies.

This plan touches one file. Everything the tracer established — the configuration check, the
normalization, the loose validation, the unconditional Resend pair, the response contract — keeps its
behavior and its relative order. The two new stages slot BETWEEN the configuration check and the
validation, turning the handler's three existing stages into the full five.

Purpose: this is the layer that makes the endpoint safe to leave publicly reachable. Double opt-in,
CAPTCHA and a distributed rate limiter are all explicitly out of scope in `REQUIREMENTS.md`, which
makes the honeypot and the in-memory counter the compensating stack rather than optional hardening.
Their ordering is the substance: D-23 puts the rate limit BEFORE the honeypot so that no path —
including the bot path — escapes the counter, which is why the counter measures attempts rather than
subscriptions.

Output: `apps/web/src/app/api/subscribe/route.ts` carrying the complete D-23 pipeline.
</objective>

  <action>
Insert D-23's stage 2 into the existing handler. It goes immediately after the configuration check
and before the body is parsed — the limit must apply to every request that gets past configuration,
including malformed ones, so that a flood of garbage bodies costs the same budget as well-formed
submissions.

Add three module-level constants above the handler: `RATE_LIMIT_WINDOW_MS` set to the expression
`10 * 60 * 1000`, `RATE_LIMIT_MAX` set to `5`, and `ATTEMPTS_SWEEP_THRESHOLD` set to `1000`. Use
integer arithmetic only — no floating point anywhere in the window or counter math. The threshold of
five per IP per ten minutes is D-10: a legitimate visitor subscribes once in their life and retries
once or twice at most, while a ten-minute window keeps the map from growing unbounded and lets a
false positive on a shared or NAT address — an office, a school, a cafe — clear itself quickly.

Add the module-scoped counter: `const attempts = new Map<string, { count: number; windowStart: number }>();`.
Put a comment directly at that declaration stating plainly that this counter lives in one serverless
instance's memory, is not shared across instances, and resets on a cold start — so it is a bulk-abuse
dampener rather than a deterministic gate. That limitation is D-09's accepted trade-off, and the
comment is where it is recorded rather than glossed; a later reader must not mistake the counter for
a guarantee it does not make. Do not add a key-value store, a cache client, or any package to close
that gap: a distributed rate limiter is explicitly Out of Scope in `REQUIREMENTS.md`.

Add `getClientIp(request: Request): string`. Read the `x-forwarded-for` header, split it on comma,
take the FIRST entry, and trim it. Vercel documents that header as the public client IP and documents
that it may be a comma-separated list when several proxies are involved, so keying on the raw string
would fragment one physical client into several counter entries as intermediaries append hops. When
the header is absent, empty, or whitespace-only, return the literal `"unknown"` — a single shared
bucket subject to the same limit, per D-12. That direction is fail-closed on purpose: stripping the
header must not become a bypass, while local development, where the header genuinely is absent, still
works against one shared key.

Add `isRateLimited(ip: string): boolean`. Read `Date.now()` once into a local and reuse it. Look up
the entry for the key. When there is no entry, or when `now - entry.windowStart` is strictly greater
than `RATE_LIMIT_WINDOW_MS`, start a fresh window by storing `{ count: 1, windowStart: now }` and
return false. Otherwise increment the existing count and return whether it now exceeds
`RATE_LIMIT_MAX`. The strictly-greater comparison is the boundary contract: a request arriving at
exactly the window length still belongs to the old window, so the fixed window never rounds in the
attacker's favor. Because a fresh window stores count 1 and the check is "exceeds max", the fifth
attempt inside a window is allowed through and the sixth is refused.

Add the map-growth bound inside `isRateLimited`, as a sweep on write: when `attempts.size` is greater
than `ATTEMPTS_SWEEP_THRESHOLD`, iterate the map once and delete every entry whose window has already
expired by the same strictly-greater comparison, then continue. Sweeping on write rather than on a
timer keeps everything inside the request path with no background work and no timer to leak in a
serverless environment.

Wire it into the handler: after the configuration check, compute the client IP, call `isRateLimited`
with it, and when the result is true return
`Response.json({ ok: false, code: "rate_limited" }, { status: 429 })`. A genuine 429 rather than a
silent fake success, per D-11: a real person caught by a shared-IP false positive would otherwise walk
away believing they subscribed. This does not conflict with SUB-03, because a 429 discloses nothing
about whether the submitted address is already in the Audience — the response body carries only the
machine code and must never gain a field, a header, or a message that varies with subscription state.

Log nothing on this path. D-25 excludes 429s from logging entirely: they are high-frequency and
low-information, and logging them would hand a bot the ability to drive a forker's log volume. The
route module must still hold exactly three `console.` call sites when this task is done. The IP key
likewise never reaches a log — it stays in process memory only, per D-24.
