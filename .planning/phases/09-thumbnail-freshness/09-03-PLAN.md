## The one thing most likely to be got wrong here

After the fix, **there is no raw S3 URL in the page source any more** — removing it is the entire fix. So
PITFALLS 14's instruction ("check the raw origin URL from page source, not the `/_next/image?...` wrapper")
does not translate literally. Its intent does, and the translation is load-bearing:

- The wrapper URL is still the wrong thing to check. Next 16's image optimizer holds a derived variant for
  at least four hours, and this window is roughly seventy minutes. 09-02's browser pass populated that cache.
  So a thumbnail that renders in a browser after the gap may simply be the optimizer replaying bytes it
  fetched before the gap, and establishes nothing.
- The right thing to check is the **proxy path itself**, requested directly, outside the optimizer. That is
  the "origin" as far as the page is now concerned, and a 200 with image bytes on it after the gap is the
  actual evidence.

The browser view still gets looked at, because what a reader sees is the requirement. It is corroboration.
Do not let it stand in for the direct request, and say which is which in the record.

**Step 1 — the first request, captured whole.** Request the home page once with the response headers dumped
alongside the body saved to a file. This single request is the whole experiment: it is the first traffic the
site has seen since the deploy-plus-gap, so it is exactly the request a real returning reader would make.
Record from it: the `x-vercel-cache` status and the `age` header if present, the `cache-control` line, and
the wall-clock UTC time.

The cache status is the honesty check on the window itself. `/` is a prerendered route with a three-minute
revalidate and a one-year expire, so a genuine post-gap first request should report a status indicating the
HTML came from a cache populated before the gap rather than a fresh render. If it reports a miss, say so and
say what that implies — most likely that something requested the site during the gap, or that a deployment
or a cache purge intervened — rather than proceeding as if the gap held.

**Step 2 — read the src out of that captured HTML.** Extract the thumbnail path from the body saved in step
1, not from a fresh request. The whole point is that this is what the stale, pre-gap HTML actually carried.
Confirm it is the stable post-id-keyed path and that no `amazonaws.com` host appears for any Notion-hosted
thumbnail. Before the fix, this is where a presigned URL minted more than an hour earlier would have been
sitting, and requesting it would have drawn a 403 from S3.

**Step 3 — the load-bearing request.** Request that extracted path directly, outside the optimizer. Record
the status, the content type, the downloaded size and the cache-control header. A 200 with a content type
beginning `image/` and a non-zero size is IMG-01's evidence: the reference embedded in hour-old HTML still
resolves to live bytes, because the URL is minted when the image is asked for rather than when the page was
last rendered. Repeat for a second and a third distinct post's thumbnail path from the same captured HTML,
so the result is not one lucky image.

**Step 4 — the post detail page, same window, same discipline.** Request one post detail page once, with
headers dumped and body saved. Record its `x-vercel-cache` status and `cache-control` line — the inherited
measurement says this route is dynamic and answers a miss on every request, so a miss here is expected and
is not a failed window. Extract the hero thumbnail's path from that captured body and request it directly,
recording the same four values. That is IMG-02's evidence.

**Step 5 — the reader's view, labelled as corroboration.** Open the home page and the post page in a fresh
incognito window and confirm every thumbnail is visible. Record it as corroborating rather than
establishing, and record why in one line: the optimizer's own cache floor of four hours spans this
seventy-minute window and 09-02's browser pass already populated it, so a rendered image here could be
replayed bytes. This is PITFALLS 14's masking layer, still live, and naming it is the difference between a
verification and a guess.

**Step 6 — record.** Append a `## Tier 3 — the idle window` section to `09-EVIDENCE.md` with: the window
start and end timestamps in UTC and the elapsed minutes; the first-request cache status for each of the two
pages; a row per thumbnail path requested with its status, content type and size; the browser observation
labelled as corroboration; and a one-line statement of the result for IMG-01 and for IMG-02 separately.

Redaction still applies: record hosts and paths only, and describe any query string by role rather than
reproducing its parameter names or values — the gate greps for those names precisely because their presence
is the reliable sign that a whole presigned URL was pasted.
And do not, under any circumstance, shorten the wait by constructing an expired presigned URL by hand — that
is the substitute PITFALLS 13 names and there is no guarantee it exercises the same path a genuinely idle
site does (D-13).
