## Phase Goal

**As a** blog visitor, **I want to** hand over my email address on the site and be told plainly whether
it went through, **so that** I get notified when a new post goes up — while a forker who never
configured Resend ships a site where that form, and the secret behind it, simply do not exist.

<objective>
Close the single Critical finding (`CR-01`) from the 2026-07-26 code-review pass: the configuration gate
at the top of `POST /api/subscribe` writes an unlatched `console.error` on every single request when the
route is unconfigured.

That branch is D-23 stage 1 — the first thing `POST` executes, ahead of `isSameOriginRequest`, ahead of
`isRateLimited`, ahead of everything. Nothing bounds it. And per `.claude/CLAUDE.md` the subscribe
feature is off-by-default ("A forker who sets no env vars sees no subscribe form and has no active email
logic"), so this is not an edge case — it is the code path every fresh fork actually runs, on a
predictable, unauthenticated, always-deployed path. An anonymous request loop drives unbounded log
volume and log cost against an operator who never opted into the feature at all.

The file already contains the fix for a structurally identical problem. `03-05` added
`originRejectionLogged` (route.ts:173, used at 240-241) for exactly this reason under D-25 — "an attacker
must not be able to drive a forker's log volume" — but applied it only to the origin-rejection site, not
to this one, even though this one runs first and has no filter ahead of it whatsoever.

Purpose: this is the one branch in the module where an unauthenticated third party controls how much a
forker's log bill grows. It is also the branch that is live on the majority of deployments.

Output: `apps/web/src/app/api/subscribe/route.ts` with the configuration-gate log latched to at most one
line per serverless instance, the 404 refusal itself deliberately left unlatched, and the message's
diagnostic content preserved — proven by a credential-free probe that sends five POSTs to an unconfigured
server and counts the log lines.

This plan is strictly additive over executed work. Plans `03-01` through `03-05` are complete with
committed SUMMARYs and are not touched.
</objective>

## The fix, stated once

```ts
// module scope, alongside `originRejectionLogged`
let unconfiguredLogged = false;

// inside POST, D-23 stage 1
if (!apiKey || !audienceId) {
  if (!unconfiguredLogged) {
    unconfiguredLogged = true;
    const missing = [...].filter(Boolean);
    console.error(`[Subscribe] Route called while unconfigured — missing: ${missing.join(", ")}. Further occurrences in this instance are not logged.`);
  }
  return new Response(null, { status: 404 });   // OUTSIDE the latch — fires every request
}
```

Three properties, each separately gated below: the latch is a plain module-scope boolean set before
logging (mirroring `originRejectionLogged` exactly, not a second mechanism); the message keeps the two
variable names and gains the "further occurrences" note that `originRejectionLogged`'s own message
already carries; and the `return` sits outside the latch block so the response is unchanged for every
caller.

**Why the message keeps its content, unlike a pure volume cut.** `originRejectionLogged`'s message is
diagnostic for an operator whose host derivation disagrees with the browser. This one is diagnostic for a
forker who simply forgot to set two env vars — and the external response is a bare 404 by design, so
there is no other channel. The operator needs to see it exactly once per instance: once is enough to
diagnose, and more than once is pure attacker-driven cost. That is what a latch buys and a deletion
would not.
