## Phase Goal

**As a** blog visitor, **I want to** hand over my email address on the site and be told plainly whether it went through, **so that** I get notified when a new post goes up — while a forker who never configured Resend ships a site where that form, and the secret behind it, simply do not exist.

<objective>
Expand the proven slice to the second template: give the `terminal` template its own CLI-prompt
visual treatment of the subscribe form (D-02) and place it below the post (D-01's terminal half),
without adding a second environment gate (D-04).

This plan exists because of a deliberate signal in `03-CONTEXT.md`: NoLog is a template other people
fork and extend, so a third-party developer building a THIRD template will read these two as the
reference. What they must copy is the shape established here — presentation varies per template, the
security boundary does not. That is why the variation lives in a `variant` prop and the gate stays
singular.

Purpose: a second template is where a single-gate design gets tested. It is also where this phase's
one genuine architectural constraint surfaces, and that constraint is not visible from
`03-CONTEXT.md` or `03-PATTERNS.md` — read the Architectural constraint section below before writing
any code.

Output: the `terminal` branch of `apps/web/src/components/subscribe/SubscribeForm.tsx`, one insertion
point in `apps/web/src/templates/terminal/PostPage.tsx`, and the Server-side slot that feeds it from
`apps/web/src/app/post/[id]/page.tsx`.

## Architectural constraint — read before writing code

`03-CONTEXT.md` D-01 says the terminal variant renders "below the post", and `03-PATTERNS.md` shows
the insertion point inside `apps/web/src/templates/terminal/PostPage.tsx`. Both are correct about
WHERE the form goes. Neither noticed that **that file carries a client directive on line 1** — it
uses `useRouter` and `useEffect` — while `apps/web/src/templates/default/Layout.tsx`, where plan
03-01 inserted the default variant, does not.

That difference is decisive. Importing `SubscribeSection` into a client module pulls the gate into
the client graph, and in client code a non-public environment variable does not merely fail to
resolve — it is replaced with `undefined` at build time. The presence check would then be permanently
false and the terminal template's form would never render, on any deployment, no matter how correctly
it was configured.

The failure mode is worse than a visible break: the secret does not leak, the SC#2 absence check
still passes, and the SC#5 bundle grep still passes. Every automated gate in this phase would read
green while SUB-01 is silently broken across half the template surface. That is exactly the class of
silent configuration failure this project's fail-closed theme exists to prevent, arriving from the
opposite direction.

**The resolution, which preserves D-01, D-02 and D-04 exactly as written:** the post route — already
a Server Component — constructs `<SubscribeSection variant="terminal" />` and passes it down as a
`subscribeSlot` prop. `TerminalPostPage` renders `{subscribeSlot}` at the D-01 insertion point. This
is the canonical Next.js pattern for a Server Component reaching a position inside a Client
Component's tree: the element is evaluated on the server, and the client receives only its rendered
output.

Nothing about the decisions changes. The placement is still below the post, inside the terminal post
page, at the exact position D-01 specifies. There is still exactly one gate and one environment read.
Only the delivery mechanism differs, because the file at the destination happens to be a client
module. Record this reconciliation in the SUMMARY so a later reader does not "simplify" the slot back
into a direct import.
