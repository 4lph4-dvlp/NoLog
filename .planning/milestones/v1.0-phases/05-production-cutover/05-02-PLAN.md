<objective>
Land the Vercel Cron entry as its own deliberate, separately-timestamped commit — strictly after the backfill confirmation Plan 05-01 recorded — and confirm the scheduled path is genuinely live by observing the registered job and one zero-risk manual trigger.

**Phase goal (verbatim, ROADMAP.md Phase 5):** "The notify path goes live in production only after the backfill has been confirmed complete, so the very first cron tick never emails a new subscriber the entire back catalog."

OPS-01's entire content is the *ordering* of this commit, which is why the plan opens with a reversibility gate and closes with a live observation rather than an inference.

Output: `vercel.json` carrying one cron entry, committed alone and pushed to `main`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet -> `GET /api/notify-subscribers` | The route is a publicly reachable URL; the scheduler is not the only caller that can reach it |
| Vercel scheduler -> the route | Vercel attaches `Authorization: Bearer $CRON_SECRET` only when that variable exists on the project; the header is the sole thing distinguishing a real tick from a stranger's request |
| git commit -> production deployment | A push to `main` is an immediate, unreviewed production change (D-04: no PR gating) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-06 | Denial of Service | Cron entry going live before the backfill is confirmed zero | high | mitigate | Wave-2 dependency on Plan 05-01; a `<precondition>` on Task 2 asserting the committed record's zero count; a blocking `checkpoint:decision` that withholds "proceed" when P1 is non-zero; and a commit-ancestry gate in `<verify>` that fails if the cron commit is not a strict descendant of the confirmation commit. This is the phase's core risk — the failure mode is a full back-catalogue broadcast to every subscriber, and a sent broadcast cannot be recalled |
| T-05-07 | Spoofing | Anonymous requests to the public notify route URL | high | mitigate | Phase 4's timing-safe `CRON_SECRET` comparison (SEC-01) is the sole trust boundary and is already shipped and live-verified (04-03-SUMMARY.md rows D6/D7). This plan adds no new auth surface; it adds a caller. Task 3 step 4 treats a 401 on the manual trigger as a real finding, which is exactly the signal that the Production `CRON_SECRET` does not match |
| T-05-08 | Tampering | Cron config written to a path Vercel does not resolve, or malformed | high | mitigate | The file path is derived from the operator-read Root Directory value (05-01 row P3), not assumed; `<verify>` parses the JSON and asserts the array length, path, and schedule; and Task 3 confirms registration in the dashboard, because a mis-placed file deploys green and registers nothing — the failure is otherwise completely silent |
| T-05-09 | Elevation of Privilege | Cron entry bundled with unrelated changes, making the ordering guarantee unauditable | medium | mitigate | The commit is asserted to contain exactly one changed file; the ancestry check is measured against the confirmation record's own add-commit rather than against a message convention |
| T-05-10 | Information Disclosure | `vercel.json` committed to a repo forkers read | low | accept | The file carries only a public route path and a cron expression, both already observable from the deployed app. No secret is placed in it — `CRON_SECRET` remains an environment variable, and the `functions` block that could leak infrastructure shape is deliberately omitted |
| T-05-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package. Its entire diff is one static JSON config file; the Package Legitimacy Gate has no applicable surface and no `[ASSUMED]`/`[SUS]` package enters the tree |
</threat_model>
