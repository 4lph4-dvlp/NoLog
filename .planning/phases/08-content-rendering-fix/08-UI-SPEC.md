# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope

This phase's entire user-visible surface is **two sentences**. Per the scope warning: not a redesign, not a
new component, not a layout change.

Today `apps/web/src/templates/default/PostPage.tsx:100` renders one sentence
(`<p className="text-text-secondary italic">Content could not be loaded.</p>`) for two different conditions.
This phase splits it into two, per CONT-05 and `08-CONTEXT.md` D-10/D-11/D-12:

1. `getPageRecordMap` **failed** (caught error) → a "could not be loaded" sentence.
2. `getPageRecordMap` **arrived but has nothing to render** → a "no content yet" sentence.

Both reuse the exact existing treatment (`<p className="text-text-secondary italic">`) verbatim — same
element, same classes, same position inside `.notion-content-wrapper`. No new component, no new token, no
layout/spacing/color/typography change of any kind.

**Explicitly out of scope, not specified here:** `PostUnavailable.tsx` (shipped/approved Phase 7, unchanged);
the `terminal` template (inactive, `08-RESEARCH.md` Finding 3 confirms zero changes needed — its
`TerminalPostPageProps` is a separate interface that never receives the new prop); the User-Agent fix,
diagnostics teardown, ISR verification (no user-visible surface); any icon or illustration for the
no-content state (a sentence is the deliverable, matching the existing fallback's shape, not
`PostUnavailable`'s card+icon shape).

**Engineering detail this UI-SPEC does not own:** which of the two sentences renders is decided by
`contentFetchFailed` (boolean, set at the `catch`) plus an emptiness check on the fetched `recordMap`
(`08-RESEARCH.md` Finding 4, `isRecordMapEmpty`-shaped) — that discrimination logic is the planner's/executor's
to implement. This contract specifies only what renders for each of the two outcomes.

## Copywriting Contract

**Locked final wording**, within D-11's shape (factual, short, one plain sentence, `text-text-secondary
italic`):

| Element | Copy |
|---------|------|
| No-content state (`recordMap` arrived, nothing to render) | **"This post has no content yet."** |
| Fetch-failed state (`getPageRecordMap` threw) | **"This post's content could not be loaded right now."** |
| Primary CTA | not applicable — neither sentence is actionable; no button/link is introduced (D-12: no recovery hint on the fetch-failed state — waiting does not help against a systemic block, so no "try again" copy) |
| Destructive confirmation | not applicable — no destructive action in this phase |

**Distinguishability (CONT-05's actual bar, ROADMAP SC#3):** the two sentences differ in their first three
words — "This post **has**" vs. "This post's content **could not**" — so a reader who is not looking for the
difference still reads two different verbs (`has` vs. `could not`) and two different subjects (`post` vs.
`content`) in the opening clause. This is a stronger signal than a difference buried mid-sentence, satisfying
the "distinguishable at a glance" requirement without any visual differentiation (icon, color, weight) — none
is warranted, since D-09/D-12 keep both states in the same plain-text register as every other fallback in this
codebase (`PostUnavailable.tsx`'s own body copy).

**Relationship to `PostUnavailable.tsx` (Phase 7, approved, unchanged):** that component's copy ("check back
in a few minutes") describes a different condition — a transient `getPost()` failure, at the whole-post level,
before any content fetch is attempted. Per D-12, this phase's fetch-failed sentence deliberately does **not**
echo that recovery language: a `getPageRecordMap` failure after Phase 8's User-Agent fix is expected to be a
systemic block, not a transient one, and promising the reader that waiting helps would be false. The two
components are not harmonized on purpose — see `08-CONTEXT.md` D-12.

**Language:** English, unlocalized — no `CONFIG.site.locale === "ko"` branching, matching the existing
`PostPage.tsx:100` precedent and `PostUnavailable.tsx`'s established pattern (Phase 7 UI-SPEC). Not reopened
here.

## UI Considerations

Two declared elements, both classified `static-content` (author-supplied, per the propose-then-confirm
rule — neither sentence is a list, form, or media element): `E1 No-content sentence` and
`E2 Fetch-failed sentence`. Because `static-content` only makes `overflow` and `long-text` structurally
applicable (per the taxonomy), and because the actual state-selection logic (which sentence renders when) is
already fully specified above in Copywriting Contract, the broader content-area behavior is additionally
covered as `E0 Post content area` (`media` + `static-content`, same classification Phase 7 gave this exact
area) to carry the `empty`/`error`/`loading`/`populated` categories this phase's real change touches.

**Resolved (explicit) — lift into `must_haves.truths`:**

| # | Element | Category | Acceptance criterion |
|---|---------|----------|------------------------------------------|
| 1 | E0 Post content area | error | When `getPageRecordMap` throws (caught), the reader sees "This post's content could not be loaded right now." — never the no-content sentence. |
| 2 | E0 Post content area | empty | When `getPageRecordMap` succeeds but the returned `recordMap` has no renderable content blocks, the reader sees "This post has no content yet." — never the fetch-failed sentence, and never the pre-Phase-8 combined string. |
| 3 | E1/E2 sentences | overflow | Both sentences render inside the existing `.notion-content-wrapper`/`<article className="max-w-none mx-auto py-8 md:px-4">` with no fixed height and no new width constraint — text wraps naturally at every viewport exactly as the single sentence does today; no truncation or clipping is introduced. |

**Dismissed (reason required):**

| Element | Category | Reason |
|---------|----------|--------|
| E0 Post content area | loading | Async Server Component; `recordMap` resolves before the response streams. No client-side loading state exists, unchanged this phase (matches Phase 7's identical dismissal for this same area). |
| E0 Post content area | populated | Happy-path rendering via `NotionPageRenderer` when `recordMap` has content is pre-existing and untouched by this phase. |
| E0 Post content area | overflow | Pre-existing `.notion-content-wrapper` behaviour for wide Notion blocks (tables, code, embeds), unchanged this phase. This phase only changes which sentence replaces the body when there is nothing to render — it never alters how present content is laid out. |
| E0 Post content area | long-text | Pre-existing `react-notion-x` block rendering for long Notion documents, unchanged this phase — same reason as `overflow` above. |
| E1/E2 sentences | long-text | Both strings are hardcoded constants in the component; no user- or Notion-supplied text can reach either `<p>`. |

**Probe accounting (no silent drops).** The `ui-consideration-probe` surfaced **10** applicable considerations
across three elements — `E1` and `E2` (`static-content` → `overflow`, `long-text` each) and `E0`
(`media` + `static-content` → `empty`, `loading`, `error`, `populated`, `overflow`, `long-text`). All 10 are
accounted for above: **4 resolved (explicit)** — counting `E1 overflow` and `E2 overflow` separately, which
row 3 covers jointly — and **6 dismissed with reasons**. `E0`'s own `overflow` and `long-text` rows were
missing from the first draft of this section and were added on reconciliation against the probe output;
without them the section would have silently dropped two considerations.

No `unclassified` candidates. No consideration left `unresolved`.

## Placement & Composition Notes

Not a template-default field, but load-bearing for the executor:

- **Where it renders:** `apps/web/src/templates/default/PostPage.tsx:96-102`, inside the existing
  `.notion-content-wrapper` div, in place of the current single `<p>`. Structure becomes a 3-way branch
  (content / fetch-failed / no-content) instead of today's 2-way (content / fallback) — see
  `08-RESEARCH.md` Finding 3 for the exact prop-shape change (`contentFetchFailed: boolean` added to
  `DefaultPostPageProps`) that feeds this branch; that prop-shape decision belongs to the plan, not this
  UI-SPEC.
- **Markup, both branches** (illustrative — the token/copy values above are the binding contract):

```tsx
{recordMap && !isRecordMapEmpty(recordMap) ? (
  <NotionPageRenderer recordMap={recordMap} />
) : contentFetchFailed ? (
  <p className="text-text-secondary italic">
    This post&apos;s content could not be loaded right now.
  </p>
) : (
  <p className="text-text-secondary italic">This post has no content yet.</p>
)}
```

- **`terminal` template:** no change. `TerminalPostPageProps` (`apps/web/src/templates/terminal/PostPage.tsx`)
  is a separate TypeScript interface from `DefaultPostPageProps` and is never passed the new
  `contentFetchFailed` prop — it compiles and renders unchanged (`08-RESEARCH.md` Finding 3, confirmed by
  direct read).
- **Nothing else on the page moves.** Header, thumbnail, comments section, and the surrounding
  `DefaultLayout` chrome (sidebars, search, profile, theme toggle) are all untouched — this phase's diff is
  contained entirely to the one conditional inside `.notion-content-wrapper`.
