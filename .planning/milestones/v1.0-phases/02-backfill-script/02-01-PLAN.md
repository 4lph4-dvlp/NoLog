<objective>
Deliver the Phase 2 backfill tool: a one-time, throttled, resumable operator CLI that marks
every pre-existing public post as `emailed`, so enabling the Phase 4 notify path never blasts
a fork's entire back catalog on its first cron tick (ROADMAP Phase 2 Goal, DATA-03).

The phase adds exactly two things: a new script at `packages/core/scripts/backfill.ts` and one
`backfill` entry in `packages/core/package.json`. It CONSUMES Phase 1's `NologClient` unchanged —
`getUnemailedPublicPosts()`, `markEmailed()`, `NotionCapabilityError`, and
`MissingEmailedPropertyError` are complete and live-verified; `packages/core/src/client.ts` is
read-only context for this phase and must not be edited (D-14 chose fixed-backoff-only over
threading `Retry-After` through `patchPage()` precisely to hold that boundary).

Purpose: resumability and check-before-write already fall out of the existing data layer for free
(`getUnemailedPublicPosts()` filters server-side; `markEmailed()` is documented-idempotent), so the
net-new logic here is deliberately small — a serial loop, a fixed 400ms sleep, an exit code, one
boolean flag, and a three-way error classification. The work is getting those exactly right, because
an `emailed` write is permanent (Phase 1 D-02, "once emailed, always emailed") and `--dry-run` is the
only gate in front of it.

Output: `packages/core/scripts/backfill.ts`, plus the `backfill` npm script entry.
</objective>

  constructor(options: { token: string; databaseId: string; fetchOptions?: RequestInit });

export declare class MissingEmailedPropertyError extends Error {}  // name = "MissingEmailedPropertyError"

  title: string;

  // must log ONLY id and title.
}

Error-class constructor messages already carry the actionable fix — print `err.message` verbatim,
do not re-word it:
- `NotionCapabilityError`: `Notion write failed for page {id}: integration lacks "Update content" capability. Grant it in your Notion integration's Developer Portal settings. (Notion said: ...)`

After the dry-run early return, declare two integer counters, `marked` and `failed`, both starting at
0, then iterate the fetched array in its returned order with a serial `for...of` loop. No
concurrency, no batching — the fixed delay only makes sense against one-at-a-time processing.

Per post, inside try/catch:
  - Success: `await client.markEmailed(post.id)`, increment `marked`, log a line carrying `post.id`
    and `post.title`.
  - `err instanceof NotionCapabilityError`: this is a SYSTEMIC setup failure, not a per-post problem —
    once the integration lacks "Update content", every remaining post fails identically. Print one
    `ABORT:` line carrying `err.message` verbatim, print a partial-count line reporting how many were
    marked and how many failed before the abort so the operator knows the state reached, set
    `process.exitCode = 1`, and RETURN out of `main()` entirely. Do NOT continue to the next post.
    This branch must be checked BEFORE the generic branch below; the ordering is the whole point of
    D-04, and getting it wrong burns the full request budget printing one identical failure line per
    remaining post.
  - Any other error: log a `FAILED` line carrying `post.id`, `post.title`, and the error's message,
    increment `failed`, and continue to the next post (D-06). A second run picks these up
    automatically, because `getUnemailedPublicPosts()` already excludes everything that succeeded —
    that is the entire resumability mechanism and it needs no extra bookkeeping.

Await `sleep(DELAY_MS)` once per loop iteration, on BOTH the success and the failure paths, so the
request spacing holds regardless of outcome. Placing the sleep on only the success path would let a
run of failures burst past the rate limit.

Exactly one counter is incremented per attempted post — never both, never neither — so the invariant
`marked + failed === (number of posts the loop attempted)` holds with no double counting.

After the loop, print the summary line in the form `N marked / M failed` using the two counters, then
set `process.exitCode` to 1 when `failed` is greater than 0 and 0 otherwise, so a caller can
distinguish a full success from a partial failure by exit status alone without parsing log output
(D-08).
