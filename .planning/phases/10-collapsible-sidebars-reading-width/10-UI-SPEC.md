# Phase 10 — UI Design Contract

> Visual and interaction contract for the collapsible sidebars + reading-width feature.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> This phase EXTENDS an existing bespoke design system — it does not invent one. Every value
> below either reuses an existing token/pattern from `globals.css` / `ThemeToggle.tsx` /
> `Profile.tsx`, or is marked `[AUTO-CHOSEN]` with a one-line rationale where CONTEXT.md left it
> to this agent's discretion.

## Spacing Scale

Declared values (must be multiples of 4) — this is the project's **existing** scale, confirmed
against `globals.css` and `Layout.tsx` (`gap-8` = 32px = `xl`), not a new invention:

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| xs | 4px | Gap between the toggle icon and its button edge (`p-2` padding is 8px, see `sm`) |
| sm | 8px | Gap between `ThemeToggle` and the avatar toggle in the pinned top-right group (`gap-2`) |
| md | 16px | Vertical gap between a panel's toggle row and the panel content below it (mobile `top-4`) |
| lg | 24px | Desktop sticky offset for the pinned toggle row (`md:top-6`) |
| xl | 32px | The grid's `gap-8` — **this is the gap D-04 requires to survive collapse untouched**; also the asides' existing `sticky top-8` offset |
| 2xl | 48px | Not used by this phase |
| 3xl | 64px | Not used by this phase |

**Exceptions:**
- Both new toggle buttons (hamburger, avatar) and the repositioned `ThemeToggle` are
  ~36px square/circle hit targets — below the ideal 44px touch target. This is **not a new
  regression**: it matches `ThemeToggle`'s already-shipped, already-in-production footprint
  (`p-2` + 18px icon ≈ 34px) exactly. Documented as an accepted, pre-existing exception, not a
  new violation introduced by this phase.
- Ring widths (`ring-2` / `ring-[3px]`, see Avatar Toggle below) are border-like decoration, not
  layout spacing, and are intentionally excluded from the 8pt grid — consistent with how
  `border-2`/`border-strong` are already used elsewhere in this codebase (`Profile.tsx:65`).

## Typography

This phase introduces **zero new visible/rendered text**. Both toggles' accessible names
(`aria-label`/`title`, see Copywriting Contract) surface only as non-rendered DOM attributes —
an `aria-label` is read by assistive tech and a `title` shows as a native OS tooltip on hover;
neither is CSS-styled body text. The table below documents the **existing, unchanged**
project-wide scale for reference only, so the checker has something concrete to check against:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`, e.g. `Profile.tsx` bio) | 400 | 1.5 |
| Label | 12px (`text-xs`, e.g. category chips) | 500 | 1.4 |
| Heading | 18px (`text-lg`, `Profile.tsx` name) | 600 | 1.3 |
| Display | not used in this phase | — | — |

No new font size, weight, or line-height token is introduced. If any plan task finds itself
adding a new visible string with its own size, that is scope creep against this contract and
should be flagged, not implemented silently.

## Component Contract 3 — `ThemeToggle` (repositioned, unchanged internals)

`ThemeToggle.tsx`'s own internals (Sun/Moon swap, `mounted` guard, chrome) are **not modified**
by this phase — only its **position** changes. **`[AUTO-CHOSEN, Claude's Discretion item]`:**
`ThemeToggle` joins the same pinned/sticky container as the avatar toggle, rather than
staying independently positioned. Rationale: D-05 places `ThemeToggle` visually adjacent to
the avatar toggle ("immediately left of the avatar"); if the avatar toggle becomes `sticky`
(required by D-06) while `ThemeToggle` stays `absolute` (its current behavior), the pair would
visually separate the instant the reader scrolls — `ThemeToggle` scrolls away while the avatar
toggle stays pinned, breaking the adjacency the layout just established. Joining one shared
sticky container keeps them paired at every scroll position. Gap between `ThemeToggle` and the
avatar toggle: `gap-2` (8px, the `sm` spacing token).

## Positioning & Sticky Contract (D-05, D-06)

**Resolved mechanism:** one shared full-width flex row, `sticky` positioned, living in normal
document flow at the top of the layout container — **not** three independently-positioned
`absolute` elements, and **not** icons nested inside each `<aside>` (CONTEXT.md explicitly
rejected the latter: a collapsed `<aside>` is 0px wide and would take its toggle with it).

```
<div className="hidden md:flex sticky top-6 z-50 justify-between items-center mb-4">
  {/* left cell */}
  <HamburgerToggle />

  {/* right cell */}
  <div className="flex items-center gap-2">
    <ThemeToggle />
    <AvatarToggle />
  </div>
</div>
```

- **Why `sticky`, not `absolute`:** RESEARCH.md Pitfall 7, confirmed by direct inspection —
  `ThemeToggle`'s current `position: absolute` (`Layout.tsx:22`) positions near the top of the
  page but **scrolls away** with the rest of the content; it does not track scroll position.
  D-06 requires both sidebar toggles to stay visible while scrolling, matching the asides' own
  `sticky top-8 self-start`. `sticky` is the only primitive that satisfies this.
- **Why one shared row, not per-toggle stickiness:** a single sticky ancestor is simpler to
  reason about for Pitfall 9 (transform/overflow on an ancestor silently breaks sticky) than
  three independently-positioned stickies, and it is what makes `ThemeToggle` joining the group
  (above) trivial — it inherits the row's stickiness for free.
- **Why the row uses `justify-between` and NOT the grid's own `grid-template-columns`:** the
  toggle row's own cells must **never** shrink when a side collapses — the hamburger must stay
  fully clickable even while the left track is `0px`, otherwise there would be no way back.
  Mirroring the animating grid columns into the toggle row would shrink the hamburger's own hit
  area to nothing exactly when it is needed most. `justify-between` inside a container that
  shares the same outer `max-w-[var(--max-content-width)]` keeps the hamburger visually over
  the left column and the ThemeToggle+avatar group visually over the right column, without
  coupling either toggle's own box size to the animating tracks below it.
- **Sticky offset:** `top-6` (24px) — `[AUTO-CHOSEN]`: matches `ThemeToggle`'s existing
  `md:top-6` desktop offset exactly (`Layout.tsx:22`), so the row's vertical position doesn't
  shift from where the reader already expects it.
- **`Layout.tsx`'s `pt-16` is removed, not preserved.** It exists today solely to reserve room
  for the currently-`absolute` `ThemeToggle` (CONTEXT.md landmine #3). Once the toggle row is
  `sticky` and participates in normal flow, it occupies its own real vertical space (`mb-4`
  below it) — an additional `pt-16` on top of that would double the gap.
- **Mobile (`< 768px`):** the entire row is `hidden` below `md` (D-08) — no toggle renders, no
  sticky row exists, `Layout.tsx`'s mobile stack (`Layout.tsx:27-38`) is visually and
  structurally untouched, satisfying SIDE-08 by simply never rendering this row in that branch.

## Transition Contract (D-11, A11Y-04)

Three distinct cases, precisely differentiated:

| Trigger | Transition? | Mechanism |
|---------|-------------|-----------|
| **Toggle click** | Yes — 200ms `ease` | Reuses `--transition-base` (`globals.css:59`) exactly as RESEARCH.md's own resolved code example specifies. `[AUTO-CHOSEN, discretion item]`: reuse the existing token rather than add a new one — RESEARCH.md's Code Example 1 already writes the mechanism this way, and introducing a second timing token for one CSS rule would add a token with no other consumer. |
| **Resize crossing the 1280px threshold (state still `null`)** | **No — instant.** | The `matchMedia` listener sets the `data-sidebar-*` attribute directly, without ever adding the transition-gating attribute below. This is D-11: a `matchMedia` flip must never visibly "whip" the sidebar along behind a dragged window edge. |
| **`prefers-reduced-motion: reduce`** | No — instant, even on click. | Belt-and-suspenders, two independent layers: (1) the click handler checks `window.matchMedia('(prefers-reduced-motion: reduce)').matches` before ever adding the transition-gating attribute; (2) the CSS transition rule itself is additionally wrapped in `@media (prefers-reduced-motion: no-preference)`, so even if the JS layer were ever bypassed, the CSS cannot animate under reduced motion. Neither layer alone is trusted as the sole guard. |

**CSS shape** (globals.css, new block — this is a *shape to replicate*, per RESEARCH.md
Pitfall 8's finding that the existing `html.transition-colors` class is dead CSS with no JS
wiring; do not attempt to hook into it):

```css
@property --sidebar-width  { syntax: '<length>'; inherits: true; initial-value: 200px; }
@property --profile-width  { syntax: '<length>'; inherits: true; initial-value: 240px; }

html[data-sidebar-left="collapsed"]  { --sidebar-width: 0px; }
html[data-sidebar-right="collapsed"] { --profile-width: 0px; }

@media (prefers-reduced-motion: no-preference) {
  html[data-sidebar-transition="active"] .sidebar-grid {
    transition: grid-template-columns var(--transition-base);
  }
}
```

**Sequencing on click** (order is load-bearing, per RESEARCH.md's Focus & Inert Sequencing —
restated here as the UI contract, not re-derived):
1. Check `document.activeElement` containment in the collapsing panel → if inside, `.focus()`
   the toggle button first (A11Y-03).
2. Set `inert` on the collapsing panel — this alone satisfies A11Y-02 regardless of how long the
   visual transition takes.
3. Add `data-sidebar-transition="active"` to `<html>` (skipped entirely under reduced-motion),
   then flip the `data-sidebar-*` attribute — this is what the CSS transition rule above reacts
   to.
4. On `transitionend` (filtered to `grid-template-columns`) or a timeout fallback
   (`--transition-base` duration + ~50ms buffer), remove `data-sidebar-transition`.

**Resize path:** steps 1-2 fire identically (focus rescue and `inert` apply to resize-driven
collapse too — A11Y-03 explicitly requires this), step 3 is skipped entirely (no transition
attribute ever added), so the width change is instant.

## Collapsed Geometry Contract (D-04, Pitfall 6)

**What visually remains when a side is collapsed: nothing.** No icon rail, no peeking stub, no
partial-width "hint" state (that is SIDE-F02, explicitly v2 and out of scope). The collapsed
side leaves exactly the 32px grid `gap` (D-04) and nothing else — this falls out of CSS Grid's
own `gap` behavior automatically (gap is between-track spacing, independent of whether a track
is `0px`), so **no code is needed to preserve it** — only avoid accidentally removing `gap-8`
from the grid container.

**How the inner content is hidden without reflow jank** (the specific mechanism this contract
requires, since it is not automatic):

1. Add `min-w-0 overflow-hidden` to **both** `<aside>` elements (`Layout.tsx:43,54`), matching
   `<main>`'s own existing `min-w-0` (`Layout.tsx:51`) — added for the exact same reason
   `<main>` needed it: a CSS Grid item's default `min-width: auto` resists shrinking below its
   content's intrinsic size, so without this the track cannot reach a true `0px`.
2. Give the `<aside>`'s **immediate child wrapper** a fixed width equal to the side's full
   uncollapsed track value — `w-[200px]` for the left wrapper, `w-[240px]` for the right —
   **never** `w-full` or `100%`. This is the detail that prevents jank: with a fixed-width
   inner wrapper, the search input, category chips, avatar, and subscribe form never reflow
   (rewrap, repack) as the outer track animates toward `0px` — they simply get progressively
   clipped by the shrinking `overflow-hidden` boundary, which reads as the content "sliding
   under the edge," not as a layout recompute.
3. `overflow: hidden`/`clip` on the `<aside>` itself does **not** break its own `sticky`
   positioning — only an *ancestor's* `overflow`/`transform` would (Pitfall 3/9); the `<aside>`
   is the element being made sticky, so this is safe by construction. Verify with the manual
   scroll test PITFALLS.md #9 already prescribes regardless, since this is new usage of
   `overflow` in this exact layout.

**Both-collapsed content-column arithmetic** (restated from CONTEXT.md/RESEARCH.md, not
re-derived): at a 1400px+ viewport, both sides collapsed → `<main>` is **1304px**, not 1368px,
because the two 32px gaps survive (D-04). This is the number the reading-width contract below
builds on.

## Reading-Width Contract (D-01, D-02, D-03)

| Property | Value |
|----------|-------|
| Applies to | **Only** `apps/web/src/templates/default/PostPage.tsx`'s root `<article>` element — the entire post-detail column (header, thumbnail, prose content, comments), since all four regions already live inside this one element. |
| Does NOT apply to | Home/Category/Search pages (`HomePage.tsx`/`CategoryPage.tsx`/`SearchPage.tsx`) — their `<main>` stays exactly as today (`min-w-0`, no max-width), so grid pages fully reclaim whatever width a collapsed sidebar frees (D-01). Also does not apply to either `<aside>`, the toggle row, or any grid-track math. |
| Cap value | `1100px` (D-02, locked) |
| Exact change | `templates/default/PostPage.tsx`'s `<article className="max-w-none mx-auto py-8 md:px-4">` → `<article className="max-w-[1100px] mx-auto py-8 md:px-4">`. **`mx-auto` is already present** — D-03's centring requirement is structurally satisfied by existing code; this is a one-token change, not a new layout. |
| Mechanism | A plain Tailwind arbitrary-value class, **not** a CSS custom property and **not** `@property`-registered. `[AUTO-CHOSEN]`: unlike `--sidebar-width`/`--profile-width`, this value never changes at runtime (it is not part of the collapse animation — it is a static ceiling on the prose column regardless of sidebar state), so it needs none of the animation machinery the sidebar tracks need. |

**Felt payoff, not just technical compliance** (the arithmetic this cap was chosen against):
at a 1400px viewport with both sidebars expanded, `<main>` is 864px and the cap has zero
effect (864 < 1100). With both sidebars collapsed, `<main>` is 1304px and the article hits the
cap at exactly 1100px — a visible **+236px** over today's 864px, split as ~102px of margin on
each side inside `<main>`. This is why D-02 rejected a 900px alternative: it would have widened
the prose by only 36px, satisfying SIDE-04's wording on paper while failing it in substance.

**Asymmetric collapse (D-03's accepted consequence):** collapsing only the right sidebar frees
240px of track width (the 32px gap SURVIVES a collapse per D-04 — it never gets double-counted),
taking `<main>` to **1104px** — this exceeds the 1100px cap, so the article centres at 1100px
with (1104-1100)/2 ≈ 2px of slack split evenly *inside* `<main>`. **Corrected 2026-08-12 by plan
10-04** (`10-EVIDENCE.md` §"Measured widths"): an earlier draft of this paragraph double-counted
the 32px gap as additionally freed on top of the 240px track (arriving at 1136px/18px), which
contradicts this same contract's own Collapsed Geometry Contract above (the gap survives a
collapse). The live-measured, plan-10-02/10-03/10-04-corroborated figure is 1104px main / 1100px
article. Because `<main>`'s own left edge did not move (only its right edge, where the collapsed
track used to be), the visually-centred-within-`<main>` article reads as shifted slightly toward
the collapsed side relative to the viewport — this is the exact, deliberately-accepted consequence
D-03 names, not a bug to fix.

| Nested-`<aside>` fix (prerequisite for a clean A11Y-01/02 target) | `Profile.tsx:63`'s root element changes from `<aside>` to `<div>`, **same className, zero visual change**. | A11Y-02 (removed from a11y tree + tab order) | `inert` on the collapsing panel — **not** `display:none`, which would kill the in-flight width transition (the transitioning property snaps instead of animating if the box leaves the render tree mid-transition). `inert` removes tab-order/a11y-tree membership immediately while the visual collapse plays out. |
| A11Y-03 (focus rescue) | Before `inert` is applied: check whether `document.activeElement` is a descendant of the collapsing panel; if so, call `.focus()` on that panel's own toggle button. **Fires identically for both the click path and the resize-driven auto-collapse path** — this is the one place resize and click behave the same (they diverge only on whether the transition plays, per the Transition Contract above). |

This relies on the browser's standard `:focus-visible` heuristic (last input modality was keyboard), not on any custom JS — no extra code is needed to make a programmatic `.focus()` show the ring in a keyboard context. |
| A11Y-04 (reduced motion) | See Transition Contract above — the reduced-motion case is fully specified there, not repeated here. |
| A11Y-05 (avatar accessible name distinct from avatar `alt`) | The avatar toggle's `<img>` uses `alt=""` (decorative) — it carries **no** text at all, so it cannot collide with `aria-label`/`title`. The button's own `aria-label`/`title` are "Show profile sidebar" / "Hide profile sidebar" (see Copywriting Contract), which are also visibly distinct in wording from `Profile.tsx`'s own avatar `alt={profile.name}` ("4lph4") — satisfied by construction on two independent axes (empty alt + distinct wording), not just one. |

## State & Persistence Contract (D-02, D-09, D-10, Claude's Discretion items)

| Property | Value |
|----------|-------|
| State shape | Per side: `null \| true \| false`. `null` = auto (follows viewport live). `true`/`false` = explicit preference, written on first toggle click, never overridden by resize again (D-10, absolute — no floor override). |
