<objective>
Close the two gaps recorded in `02-VERIFICATION.md` that reverted DATA-03 from Complete to Gaps Found.

**Gap 1 — incomplete systemic-abort classification in the write loop.** `backfill.ts` only treats
`NotionCapabilityError` as systemic, and only in the outer per-post catch. The rate-limit retry's
inner catch has no error-class check at all, and `MissingEmailedPropertyError` — which `patchPage()`
can throw on a mid-run schema change — is classified as systemic only in the initial-fetch catch,
never inside the loop. Both holes violate D-04's contract: one systemic condition must produce one
abort, never one failure line per remaining post.

**Gap 2 — COVERAGE.md fails its own validator.** `api-coverage.verify-pre` returns
`block: true, passed: false` on two over-length cells, and the phase cannot seal until the matrix
validates.

Purpose: DATA-03's "safely re-runnable" promise is only meaningful if a systemic failure stops the
run and says so once. A backfill that burns 400ms per post through a whole back catalog printing
identical failures — the exact anti-pattern D-04 was written to prevent — is the failure mode this
closes, and it is currently reachable through the ~1s retry window and through any mid-run schema
change.

Output: a hardened `backfill.ts` write loop and a validator-clean `COVERAGE.md`.
</objective>

This is the thin end-to-end slice for the defect: drive one systemic condition from the point it is
thrown, through classification, to a single abort message and a non-zero exit — at every place in the
loop where such a condition can surface. There is no horizontal expansion afterward; the fix is the
slice.

Add a module-level type-guard function immediately after the existing `isRateLimited` definition:

  `function isSystemicAbort(err: unknown): err is NotionCapabilityError | MissingEmailedPropertyError`

Its body returns true when `err` is an instance of `NotionCapabilityError` OR an instance of
`MissingEmailedPropertyError`, and false otherwise. Use `instanceof` only. Do NOT pattern-match the
error message text here — message text is Notion-controlled data, and the whole point of putting this
guard ahead of `isRateLimited` is that a typed class identity outranks a string that a remote service
chose. Both classes are already imported at the top of the file from `../dist/index.js`; no import
change is needed.

Add a second module-level function immediately after it:

  `function reportSystemicAbort(err: NotionCapabilityError | MissingEmailedPropertyError, marked: number, failed: number): void`

Its body performs exactly three statements: `console.error("ABORT:", err.message)`, then a second
`console.error` printing the partial-count line in the same shape the existing abort branch already
uses (the two counters plus a parenthesized note that this is a partial, aborted run), then
`process.exitCode = 1`. Centralizing these three statements is what guarantees the "exactly one ABORT
message" property structurally rather than by convention: both loop abort sites emit through this one
function, so they cannot diverge in wording or forget the partial count. This function does not and
cannot return out of `main()` — each call site is responsible for its own `return` on the very next
line.

Restructure the OUTER per-post catch (currently the `err instanceof NotionCapabilityError` /
`isRateLimited(err)` / else chain) so the first branch tests `isSystemicAbort(err)` instead of the
single-class check. That branch calls `reportSystemicAbort(err, marked, failed)` and then `return`s
out of `main()` immediately — it must not fall through, must not increment either counter, and must
not reach the trailing `sleep(DELAY_MS)`. Branch ORDER is load-bearing and must be exactly:
`isSystemicAbort(err)` first, `isRateLimited(err)` second, generic per-post failure last. Placing the
rate-limit test first would let a 403 or a schema 400 that happens to be shaped like a rate-limit
response take the retry path, which is the ordering bug this task exists to prevent.

Add a matching first branch to the RETRY's INNER catch (the `catch (retryErr)` block). It tests
`isSystemicAbort(retryErr)`, calls `reportSystemicAbort(retryErr, marked, failed)`, and `return`s out
of `main()`. It must appear ahead of the existing per-post failure handling in that block, so the
existing `retryMessage` extraction, `FAILED` log line, and `failed += 1` become the else path rather
than the unconditional path. This is the ~1s window the verifier reproduced: capability revoked
between the rate-limit response and its retry currently produces a per-post failure and a loop that
keeps running.

Counting rule for both new abort branches, stated explicitly so it is not guessed at: the post being
processed at the moment of abort is counted in NEITHER bucket. It was neither successfully marked nor
resolved as a per-post failure — the run stopped on it. The printed counts are therefore the counts of
posts fully resolved before the abort, which is exactly what the existing capability-abort branch
already reports. Do not add a `failed += 1` before either `reportSystemicAbort` call.

Leave everything else byte-for-byte alone. Specifically do NOT touch: the initial-fetch catch block
and its D-05/D-15 branches (verified and owned by plan 02-01 — restructuring it here would re-open a
predicate this plan does not own), `isRateLimited` and its message-prefix anchoring, `DELAY_MS`,
`RETRY_BACKOFF_MS`, the `sleep` helper and its single unconditional call per iteration, the `parseArgs`
strict-mode flag gate, the dry-run path, the final summary line, or the closing exit-code assignment.
Do not modify `packages/core/src/client.ts`. Do not add a dependency or an npm script.

Update the comment on the outer abort branch so it names both systemic conditions (revoked write
capability; the `emailed` property disappearing from the schema mid-run) rather than only the
capability case, and add a one-line comment on the retry's new branch recording why it exists — a
systemic condition can first surface inside the retry window, and treating it as per-post noise there
reintroduces the exact behavior D-04 forbids.
  </action>
