## Two landmines — read these before writing a line

**Landmine 1 — `research/ARCHITECTURE.md` §1's option (b) is wrong and would ship the bug unfixed with
every check green.** It proposes an un-`cache()`-wrapped export off the existing `nologClient` singleton,
citing `getUnemailedPublicPosts()` as precedent. But `apps/web/src/lib/notion.ts:8-17` bakes
`fetchOptions: { next: { revalidate: CONFIG.revalidate, tags: [NOTION_CACHE_TAG] } }` into the
**constructor**, and `packages/core/src/client.ts:311-316`'s `getPost()` spreads `...this.fetchOptions`
into its own `fetch()`. Dropping React's `cache()` wrapper removes per-render memoization only; the
180-second Next Data Cache entry survives untouched. Only a **second `NologClient` instance** built with
`fetchOptions: { cache: "no-store" }` actually bypasses it (D-14, `09-RESEARCH.md` Finding 2 / Pitfall N1).
Task 3 gates this explicitly.

one field to the **local** type first. `packages/core` stays untouched — REQUIREMENTS.md D-05 governs the
published npm package, and the local mirror is not it (`09-RESEARCH.md` Finding 1 / Pitfall N2).

**Step 2 — the proxy route.** Create `apps/web/src/app/api/thumbnail/[id]/route.ts`.

Module scope, in this order:
- `export const runtime = "nodejs";` — copy the declaration verbatim from
  `apps/web/src/app/api/subscribe/route.ts:3`.
- `freshNologClient`, a **second, separate** `NologClient` imported from `@4lph4/nolog-core` and
  constructed with `token` from `process.env.NOTION_TOKEN`, `databaseId` from
  `process.env.NOTION_DATABASE_ID`, both with the same empty-string fallback the shared module uses, and
  `fetchOptions` set to an object whose only key is `cache` with value `no-store` (D-14). It must NOT
  import the shared cached client module under `@/lib` — that module's singleton carries a
  180-second Data Cache entry in its constructor which survives removal of any React memoization wrapper,
  and reusing it would read from the exact cache this phase exists to bypass. Write the reason as a
  comment above the instance so a future reader does not "simplify" it back.
- `ALLOWED_HOSTS`, a `Set<string>` holding exactly the two literals `s3.us-west-2.amazonaws.com` and
  `prod-files-secure.s3.us-west-2.amazonaws.com`, mirroring `apps/web/next.config.ts`'s
  `images.remotePatterns` (IMG-03). Duplicate the two literals rather than importing `next.config.ts` —
  `09-RESEARCH.md` Assumption A1 flags that import as unverified with no precedent in this repo, and
  `09-PATTERNS.md` names duplication the safer default. Add a comment naming `apps/web/next.config.ts` as
  the source of truth so the two lists are found together if a third region host is ever added.
- `THUMBNAIL_CACHE_CONTROL`, a string constant with the value `public, s-maxage=14400, immutable` (D-06,
  and the discretionary value 09-CONTEXT left open). Comment the reasoning: 14400 seconds matches Next 16's
  own `images.minimumCacheTTL` default of four hours, so the CDN holds these bytes for exactly as long as
  the image optimizer would independently hold its derived variant anyway — the Function ends up running on
  the order of once per image per four hours instead of once per reader, which is what makes D-05's
  byte-proxying affordable, while adding no staleness beyond what the platform already imposes when an
  operator swaps a thumbnail in Notion. No browser-facing `max-age` is set, because the browser never
  requests this path directly: Next's image component rewrites it to the optimizer path, and the optimizer
  sets its own reader-facing headers.

Then `export async function GET`, taking the request as an unused first parameter and destructuring
`params` typed as a promise of an object with an `id` string, matching Next 16's route-handler signature.
Inside, in exactly this order, each rejection returning a `Response` with a **null body** and the stated
status:

1. Await `params`, then pass the `id` segment through `parsePageId` imported from `notion-utils`. A falsy
   result is a 400. From here on only the parsed value may reach any downstream call — never the raw route
   segment. This is the identical discipline `apps/web/src/lib/post-availability.ts:69-76` already
   establishes, and it is load-bearing rather than cosmetic: both of `parsePageId`'s regexes are
   word-boundary matched and not anchored, so a real page id embedded inside a longer garbage string still
   parses, and only the parsed value is safe to build a URL from (D-07).
2. Call `getPost` on `freshNologClient` with the parsed id. It answers `null` for a missing page, for any
   Notion-side error, and for a page whose `status` is not `public` — reusing it therefore inherits the
   unpublished-post filter for free rather than duplicating property-extraction logic that could drift
   (`packages/core/src/client.ts:328-334`). A null result is a 404. Also answer 404 when the post's
   `thumbnailType` is not the literal `"file"`, or when its thumbnail field is falsy: that is IMG-05's
   server-side half — an external thumbnail is never served through this route even if a caller
   hand-constructs the path.
3. Parse the post's thumbnail value with the `URL` constructor inside a try/catch; a throw is a 400.
   Compare the parsed `hostname` against `ALLOWED_HOSTS` and answer 400 when it is absent (IMG-03).
4. Fetch the resolved URL with two options: `redirect` set to `"error"`, so a 3xx from an otherwise
   allowlisted host rejects the promise instead of silently walking off the allowlist, and a `User-Agent`
   header set to `NOLOG_USER_AGENT` imported from `@/lib/notion-x` — that constant exists specifically
   because this phase was expected to reuse it, and it is honest self-identification, not browser
   impersonation. Wrap the call in try/catch; any throw, including the redirect rejection, is a 502.
5. Read the upstream `content-type` header. Answer 502 when the upstream response is not ok, when the
   header is absent, or when it does not begin with `image/` — checked from the headers alone, before any
   part of the body is touched, so the guard costs nothing against the streaming design (IMG-03).
6. On success return a `Response` constructed from the upstream response's `body` directly. Never call
   `.arrayBuffer()`, `.blob()` or `.text()` on it first — those buffer the whole image in the Function's
   memory and defeat D-05's entire point. Set three response headers: the asserted upstream content type,
   the `cache-control` constant, and `x-content-type-options` set to `nosniff` as a second layer behind
   the content-type assertion, since this route is same-origin and a mis-typed body would otherwise be
   sniffable.

Two hard rules on the failure paths: every rejection carries a null body and no message, and no response
body or header may ever contain upstream response text, the resolved URL or any part of its query string,
a `process.env` value, or a caught error's message. The Function holds `NOTION_TOKEN` and a signed S3 URL
and neither may leave it. Log rejections with this repo's bracket-prefix convention through `console.warn`
or `console.error` with a `[Thumbnail]` prefix, and keep the resolved URL's query string out of the log
line too. Catch with no binding or with `unknown`, and never throw out of the handler.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → `/api/thumbnail/{id}` | Anonymous, unauthenticated, caller-controlled path segment crosses here. The route is publicly reachable and needs no secret. |
| Route → `api.notion.com` | Outbound request authenticated with `NOTION_TOKEN`, a server-only secret. |
| Route → Notion's S3 hosts | Outbound request to a URL the route resolved, never one the caller supplied. |
| Route → reader's browser | Response body is bytes from a third-party origin, served under this site's own origin. |
| Server Component → `PostThumbnail` client island | Already-fetched `Post` data crosses into client code; no secret and no env-gated module crosses with it. |
