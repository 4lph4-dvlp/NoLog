## Phase Goal

**As** the future notify/backfill code path (the API consumer of `NologClient` — Phase 4's cron route and Phase 2's backfill script), **I want to** query which public posts have not been emailed yet and durably mark one as emailed once its send succeeds, distinguishing a missing-write-capability 403 from other failures, **so that** subscribers are notified exactly once per post, ever, and a missing Notion setup fails loud instead of silently storming duplicate emails.

> Note: the ROADMAP `**Goal:**` line for this phase is written as a backend capability statement, not the canonical "As a / I want to / so that" user-story form. This phase is a backend-only data-layer extension with no end-user UI surface (CONTEXT.md phase boundary), so the story above is framed for its real, named actor — the internal API consumer (RESEARCH.md's future callers), not an invented end user. If a canonical user story is wanted, run `/gsd mvp-phase 1`.

<objective>
Extend `NologClient` (`packages/core/src/client.ts`) with the write-side data layer for the email-subscription feature: a query for public-but-unemailed posts, a durable "mark emailed" write, and two typed, `instanceof`-checkable error classes for the two fail-loud setup failures the user locked in (D-01 missing `Emailed` property, D-03 missing "Update content" capability / 403). No route handlers, no email sending, no subscribe form — the data-layer contract only. The future callers (Phase 2 backfill, Phase 4 notify route) do not exist yet; this phase delivers the contract they will consume.

Purpose: Establishes the exactly-once-per-post notification substrate and makes the two most dangerous silent-failure modes (duplicate-email storm on a missing capability; unexplained raw error on a missing property) loud and programmatically catchable.

Output: Extended `NologClient` + `Post.emailed` field + two committed manual-verification scripts proving the live-Notion behaviour the phase's success criteria require.
</objective>
