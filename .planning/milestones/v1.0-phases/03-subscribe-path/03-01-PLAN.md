## Phase Goal

**As a** blog visitor, **I want to** hand over my email address on the site and be told plainly whether it went through, **so that** I get notified when a new post goes up — while a forker who never configured Resend ships a site where that form, and the secret behind it, simply do not exist.

<objective>
Deliver the Phase 3 tracer: one production-quality path running end to end from the default
template's server render, through the single environment gate, into the client form, across the
network to a Node-runtime route handler, through normalization and validation, into the Resend
contacts API — and back out as a machine-readable code the form turns into locale-correct copy.

This is the phase's whole architecture proven on the agent's best tokens, before anything expands
outward. Plan 03-02 adds the abuse-resistance stages (D-09 through D-13, completing D-23's pipeline
order). Plan 03-03 adds the second template (D-01's terminal half and D-02's CLI-prompt variant).
Neither rewrites what lands here.

Purpose: the hardest guarantee in this phase is a negative one — the secret must never reach the
client and the form must never appear on an unconfigured fork (SEC-03, SUB-02). That is a property of
WHERE the environment read lives, so it has to be settled in the first slice rather than patched on.
The second-hardest is that a duplicate submission is indistinguishable from a fresh one (SUB-03);
D-17's unconditional create-then-update makes that structural — a property of the ABSENCE of a branch
— which likewise cannot be retrofitted credibly.

Output: `apps/web/src/lib/email.ts`, `apps/web/src/components/subscribe/SubscribeSection.tsx`,
`apps/web/src/components/subscribe/SubscribeForm.tsx`, `apps/web/src/app/api/subscribe/route.ts`, the
`resend` dependency in `apps/web/package.json`, and two insertion points in
`apps/web/src/templates/default/Layout.tsx`.
</objective>

which is precisely the enumeration oracle SUB-03 forbids. So: log a create error per the logging

result.

  - update returns no error -> `Response.json({ ok: true }, { status: 200 })`.
  - update returns an error -> `Response.json({ ok: false, code: "server_error" }, { status: 500 })`,

    success must not be reported. Add no retry loop inside the route: a visitor-facing serverless
    request must not wait on a second failure, and the whole path is idempotent, so the visitor's own
    retry is the recovery mechanism. A genuinely broken configuration fails both calls and lands here

`server_error` branch instead of escaping as an unhandled 500 with a stack trace.

subscriptions — with the address forbidden, such a line could only report that one happened, which
Vercel's short log retention makes useless anyway. Neither call site, and no comment sharing a line
with either call site, may reference `normalizedEmail` or the address in any form: not the full
value, not the domain alone, not a hash.

Keep the two log strings distinguishable from each other, create versus post-create update, so a
forker can tell which call failed. But do NOT make either string vary by whether the contact already
existed: a differing log line for an already-subscribed address is the same enumeration oracle as a
differing response body, just aimed at a different reader.
