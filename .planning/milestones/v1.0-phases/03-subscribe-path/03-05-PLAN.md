## Design decision record — the request's own host, not the configured one

The reviewer's illustrative snippet compares `Origin` against `CONFIG.site.url` from `site.config.ts`.
This plan deliberately does NOT do that. The decision and its reasoning are recorded here because it is
the load-bearing choice in this plan.

### The two candidate anchors

| Anchor | Production domain | Vercel preview deployment | `localhost` dev | Forker who never edited the config |
|---|---|---|---|---|
| Static configured site URL | works | **rejected** — preview URLs are auto-generated and differ from any value a forker set | **rejected** — no configured value is ever `http://localhost:3000` | **rejected**, and simultaneously **under-protecting**: the template author's domain becomes a valid submitting origin on someone else's deployment |
| Request-derived host | works | works | works | works |

`README.md` § Configuration documents the field as "**Site URL**: Your production domain" — production,
by its own description. Anchoring a security control to a value documented as covering one of the three
environments a forker actually runs in would make normal pre-merge testing fail closed, in a project
whose stated core value is that there is "no infrastructure to provision, no service to babysit".

The static anchor's worst property is not the false positive, though — it is that the false positive and
the under-protection are **the same bug**. A forker who forgets to edit the value gets a deployment
where their own visitors are refused and the template author's domain is trusted. Nothing in the code
can detect that state, because a stale string is indistinguishable from a deliberate one.

### Chosen approach

Derive the expected host from the request itself: read `x-forwarded-host`, then `host`, first non-empty
match winning; lowercase it; compare it against `new URL(origin).host` (which is host plus port,
omitting a default port, and already lowercased by the URL parser). No static configuration, no import,
no env var, nothing to keep current.

**Union with the configured value was considered and rejected.** A union can only ever ADD allowed
origins, and the one it would add is the possibly-stale default — the exact value with the worst
failure mode. It buys nothing: an `Origin` that equals the request's own host already passes.

### Why comparing two request headers is a real control and not circular

For the threat that matters here — a cross-site page driving a visitor's browser — both sides of the
comparison are set by the browser and neither can be set by the attacker's page script:

- `Origin` is a **forbidden request header** (MDN, fetched 2026-07-26): "scripts cannot manually set this
  header". The browser sets it to the attacker's own origin.
- `Host` is likewise a forbidden request header; the browser sets it to the authority actually being
  requested — the blog's.
- `x-forwarded-host` is not forbidden, but a cross-origin `fetch` that sets a non-safelisted header
  becomes a preflighted request; this route emits no CORS response headers, so the preflight fails and
  the request is never sent. Under `mode: "no-cors"` a non-safelisted header cannot be set at all. A
  cross-site HTML form submission cannot set headers whatsoever.

So on a browser-driven cross-site request the comparison is attacker-origin against blog-host — a
mismatch, by construction. **What this control does not do, stated plainly:** a scripted (non-browser)
client can send any `Origin` it likes and passes trivially. No Origin check anywhere can constrain that
client. What the check removes is the attacker's ability to borrow *other people's* browsers and *other
people's* IP addresses — which is precisely the amplification the review identified ("many distinct
visitor IPs each firing one request"). A scripted attacker falls back to their own addresses, where
`03-04`'s rate limiter applies. See `<threat_model>` T-03-21 for the residual.

**Third source, the fail-open decision.** `https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin`

browser-driven requests, where the browser (not the platform) is what makes both headers trustworthy. A
client that can forge `x-forwarded-host` can forge `Origin` too, and is out of the control's reach
either way. Nothing here rests on a claim the docs do not make.

### The "no Origin header" decision — allow, and why

`SubscribeForm.tsx` was read for this. It submits **only** through `fetch("/api/subscribe", { method:
"POST", headers: { "Content-Type": "application/json" }, ... })` inside an `onSubmit` handler that calls
`e.preventDefault()` first. The `<form>` element carries no `action` and no `method`. **There is no
no-JavaScript submission path in this app**, so every real submission is a same-origin POST `fetch`, and
per MDN above a browser adds `Origin` to exactly that. A modern browser never omits it on a POST.

Therefore an absent `Origin` identifies a non-browser client — and that client can set the header to
anything, so refusing on absence buys nothing against an adversary while refusing honest non-browser
traffic: this plan's own credential-free probes, a forker's `curl` smoke test, an uptime monitor.

There is also a concrete, checkable benefit. Every POST snippet in `03-VALIDATION.md` and every probe in
`03-04-PLAN.md` sends no `Origin` header (all of them do send `Content-Type: application/json`, so the
media-type gate in T2 does not disturb them either). Allowing on absence means **the entire existing
non-regression suite keeps its expected results unchanged** — the sweep in `<verification>` is a genuine
re-run of previously-green checks, not a rewritten test whose passing would prove much less.

The literal opaque origin value is a separate case and IS refused: per MDN it is produced by sandboxed
iframes, CSP-sandbox documents, `data:`/`blob:`/`file:` documents and cross-origin redirects, none of
which is this app's own page, and an attacker can deliberately induce it (a `no-referrer` policy or a
sandboxed frame) to turn a naive presence check into a bypass. It is refused explicitly rather than left
to `URL` parsing throwing, so the intent is legible in the source and assertable in a gate.

**`Referer` fallback considered and rejected.** It would only help if a browser sent `Referer` but not
`Origin` on a POST, which per MDN none does, while `Referer` is stripped by privacy tooling and proxies
far more often than `Origin` — pure false-positive surface for zero added coverage. Single signal.

### Pipeline placement — after the configuration 404, before the rate limit

- **Not before the configuration 404.** D-22/SUB-02 require an unconfigured deployment to be externally
  indistinguishable from one that never had this route. A cross-origin refusal emitted before the 404
  would answer a scanner's real question — *does this route exist* — so the 404 stays strictly first.
- **Before the rate limit.** Two reasons, the second decisive. A refusal is two header reads and a string
  compare, cheaper than the counter's map write. And if the check ran *after* the limiter, an attacker
  driving thousands of victim browsers would spend rate-limit budget keyed by *victim* IP addresses:
  with `03-04`'s `ATTEMPTS_MAX_KEYS` ceiling in place, that fills the map and collapses genuinely new
  visitors into the shared overflow bucket, so the cross-site attack would degrade into a denial of
  service against real subscribers. Refusing first makes forged traffic cost the limiter nothing — and
  that ordering is directly asserted by a probe (eight forged POSTs, all 400, zero 429).

D-23's stage list gains one stage at position 2 and one precondition inside the existing body-parse
stage. **No pre-existing stage changes its relative position.**

### Refusal response — the existing 400, unchanged

The refusal returns `Response.json({ ok: false, code: "invalid_email" }, { status: 400 })` — byte-identical
to what an unparseable body already produced before this plan. Justification against SUB-03: the module's
observable status set and machine-code set are unchanged, asserted by set comparison, so there is provably
no new response shape for a prober to correlate. It also denies a cross-site attacker any confirmation
that an origin control exists at all — the response reads as "we didn't like your email", which is the
same posture D-13 takes with the honeypot. D-21 fixes the code set to three; a fourth code firing only for
refused origins would be a new signal for no benefit.

It deliberately does **not** reuse the honeypot's fake `200 {"ok":true}`. The honeypot fake-succeeds
because a *legitimate-looking* client must learn nothing about being detected; a forged cross-site request
is not ambiguous and gets a plain refusal.

### Logging — one new site, at most once per instance

A fourth `console.error` is added, superseding `03-04`'s exactly-three truth (see § Truths this plan
supersedes). The argument is the file's own precedent: the configuration-404 branch already reasons that
"the operator log below is the one place the missing detail is spelled out" *because* the external
response was deliberately made uninformative. The same is true here and more sharply — a deployment whose
host derivation somehow disagrees with the browser's `Origin` would refuse every submission while telling
each visitor their email address looks invalid, and there would be no other way for the operator to find
out. Choosing an uninformative response obliges us to make the log informative.

Bounded to **once per serverless instance** by a module-scoped latch, for the reason D-25 gives for not
logging 429s and honeypot drops: an attacker must not be able to drive a forker's log volume. A
misconfiguration is deterministic, so the first line carries the whole diagnosis; attack traffic costs one
line per cold start. `Origin` is not PII the way an address or an IP is, so D-24 is not in tension — but
it is attacker-controlled text, so both logged values are length-bounded and escaped (see T1).

### Requirements coverage note (why `requirements` is empty)

`requirements: []` is deliberate and is not an omission. `REQUIREMENTS.md`'s Subscribe block is
SUB-01 (a visitor can submit), SUB-02 (absent when unset), SUB-03 (no enumeration oracle), SUB-04
(honeypot **and** per-IP rate limiting). SEC-03 is the server-side render gate; SEC-01/SEC-02 are

authorization. Claiming SUB-04 would be force-fitting: the review states outright that the honeypot does

## Flagged assumptions (surfaced, never silently dropped)

- **`request.headers.get("host")` is readable in a Next.js `nodejs` route handler.** Documented by Vercel
  with a Next.js App Router example reading exactly that (§ Header verification record), and required by
  HTTP/1.1 on every request. Not separately unit-asserted — but it is **self-verifying under T1's probe
  session B**: if the header were unreadable the derivation would yield nothing, the predicate would
  refuse, and the same-origin request would return `400` instead of the asserted `500`. A false assumption
  here fails loudly rather than silently.
- **The comparison is host-and-port only, not scheme-inclusive.** `x-forwarded-proto` was read during
  planning and deliberately not used: adding it would introduce a third header dependency to close
  T-03-26, a `low` residual with no reachable exploit on the only supported host. Recorded rather than
  omitted.
- **Browser `Origin` behavior is taken from the MDN reference, not observed in a browser.** No browser
  runs in this execution environment. The probes drive `curl`, which can present any header including
  none — that is precisely what makes them credential-free, and also the honest limit on what they prove
  about real browser behavior. It is why the three claims the design rests on (`Origin` present on
  same-origin POST, `Origin` a forbidden request header, the enumerated opaque-origin cases) were verified
  against a documentation source rather than inferred from the probes.
- **A cross-origin `fetch` declaring `application/json` is preflighted and this route fails that
  preflight.** Derived from the CORS-safelisted media-type list (`application/x-www-form-urlencoded`,
  `multipart/form-data`, `text/plain`) plus the absence of any CORS response header in this repo — no
  `middleware.ts` exists at either `apps/web/middleware.ts` or `apps/web/src/middleware.ts`
  (checked during planning), and the route sets no `Access-Control-*` header. Not observed in a browser.
  T2's value does not depend on it: the server-side refusal stands alone, and the preflight is the bonus.
- **The user story at the top of this plan is reused, not authored.** ROADMAP's Phase 3 `**Goal:**` line
  is not in user-story format. Rather than invent one for a gap-closure plan, the already-approved story
  from `03-02-PLAN.md` is reused verbatim. If a canonical story is wanted on the ROADMAP line, that is
  `/gsd mvp-phase 03`, not this plan.
- **`requirements` is deliberately empty.** See § Requirements coverage note. Not an omission, and not
  force-fitted to SUB-04.
- **`03-REVIEW.md`'s `CR-01` label is reused across two different findings.** Disambiguated throughout as
