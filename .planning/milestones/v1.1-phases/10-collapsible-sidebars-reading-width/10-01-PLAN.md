<planning_resolutions>
Two gaps in `10-UI-SPEC.md` are resolved here rather than left for the executor. Both are recorded because
following UI-SPEC literally would have regressed a requirement.

**R-1 — `ThemeToggle` must keep rendering below `md`.** UI-SPEC's Positioning Contract puts `ThemeToggle`
inside the `hidden md:flex` pinned row AND separately asserts the mobile stack is "visually and
structurally untouched". Those are inconsistent: `Layout.tsx:22`'s wrapper carries no `hidden`, so
`ThemeToggle` renders at **every** viewport today, mobile included. Moving it into a desktop-only row
would delete the mobile theme toggle — a functional regression against SIDE-08 / ROADMAP SC#2.
**Resolution:** two single-viewport renders. `Layout.tsx` keeps an `absolute top-4 right-4 z-50 md:hidden`
wrapper holding `<ThemeToggle />` for mobile; `SidebarShell`'s `hidden md:flex` row holds a second
`<ThemeToggle />` for `md`+. Exactly one is ever visible; `next-themes` shares one context across both.

**R-2 — the pinned row and the sticky asides would overlap when scrolled.** UI-SPEC pins the row at
`sticky top-6` (24px) and leaves the asides at their current `sticky top-8` (32px). Both stick, so once
the reader scrolls, the row's ~36px box (24px→60px) sits on top of each aside's first 28px. UI-SPEC does
not address the collision. **Resolution:** raise both asides to `sticky top-16` (64px), which clears the
row's stuck bottom edge (60px) by 4px. Both asides are `hidden md:block`, so this has zero mobile effect.
Also `Layout.tsx`'s container padding becomes `pt-16 md:pt-6` — mobile keeps its existing 64px clearance
for the mobile `ThemeToggle` (removing it outright would move the mobile stack, again against SIDE-08),
while `md`+ drops to 24px so the newly in-flow row starts exactly at its own sticky offset and does not
jump on first scroll.
</planning_resolutions>

<assumption_delta_decision>
**Noun now primary:** *document-element state family* — `<html>` carries two of them after this phase
(`next-themes`' `.dark` class, and this phase's `data-sidebar-*` attributes).

**Decision: `add-alongside`.**

The two detector signals ("a script *alongside* the existing next-themes setup", "CSS *custom*-property
overrides") are cue matches on incidental prose, not a genuine singular→plural or derived→chosen
transition. But the `promote` reading is real and was considered on its merits, not dismissed: this phase
does add a second independent pre-paint writer to `document.documentElement`, which is a true "second X
where there was one" on the document-element-state axis. A promote would mean generalizing both families
through one shared state registry.

Rejected because the two families are orthogonal in every dimension that would make a registry pay —
different mechanism (class vs. attribute), different storage keys, different value vocabulary, no read or
write path in common, and no ordering dependency between them. More decisively, half the surface lives
inside a third-party bundle: routing `next-themes` through a shared registry means forking or wrapping
its own injected script, which costs more than the coupling it removes and violates D-07's no-new-
infrastructure constraint in spirit.

**Accepted debt:** two independent pre-paint writers to `document.documentElement`, each with its own
flash-prevention mechanism, and no single place that describes the element's full state contract.

**What would force a promote later:** a third independent `<html>`-state family arriving, or the first
genuine dependency between the two — sidebar CSS needing to read theme state, a flash caused by the two
scripts' execution order, or a shared "disable transitions during change" need. Any one of those turns
the registry from indirection into the cheaper option.

This checkpoint never blocks the phase.
</assumption_delta_decision>

never returned, never concatenated into an attribute value, and never used as a class name (ASVS V5,
threat T-10-01). `readSidebarPref` wraps `localStorage.getItem` in try/catch and returns `null` on throw
(private-mode / disabled-storage). `writeSidebarPref` wraps `setItem` in try/catch and swallows the
throw. `setSidebarAttr(side, collapsed)` writes `document.documentElement.setAttribute(sidebarAttrName(side), collapsed ? "collapsed" : "expanded")`
— the two value words live only in this file, alongside `initSidebarState`, so the vocabulary is
single-file auditable (this is the "explicitly commented deliberate duplication" CONTEXT.md landmine 2
permits, and the comment must say so).

`initSidebarState(breakpointPx, storageKeyPrefix, attrPrefix)` is the function serialized into the inline
script. Its body must reference ONLY its own three parameters and browser globals (`document`, `window`,
`localStorage`) — no import, no module-scope constant, no closure of any kind, because `.toString()`
captures the body text only. Write it in ES5-shaped JS (`var`, `function`, plain `if`, no optional
chaining, no nullish coalescing, no `async`, no class fields, no TS-only syntax beyond parameter type
annotations) so the emitted string cannot acquire a transpiler helper reference. Behaviour: compute
`isNarrow` from `window.matchMedia("(max-width: " + (breakpointPx - 1) + "px)").matches`; for each of
`"left"` and `"right"`, read `storageKeyPrefix + side` from `localStorage` inside try/catch, apply the same
allowlist parse inline, use the parsed preference when non-null and `isNarrow` otherwise, and
`setAttribute(attrPrefix + side, collapsed ? "collapsed" : "expanded")` on `document.documentElement`.
It writes BOTH sides deliberately — the right attribute has no CSS consumer until plan 10-02, so it is a
no-op there, and writing both here means the script and its parse logic are authored once. Add a JSDoc
block stating the serialization constraint and the reason (matches the technique read out of the installed
`next-themes` bundle, per PATTERNS.md).
